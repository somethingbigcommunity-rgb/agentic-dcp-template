# AGENTS.md

Global rules (prompt level L1) for every agent working in this repository, in any harness (GitHub Copilot, Antigravity). This repository follows the **Agentic Software Engineering (ASE) harness v0.2**.

## Project configuration

Filled in by `/ase-setup` during P0 (new project, `remote` Git mode) or by `/ase-adopt` (existing or local repository, `local` Git mode). In a new project with no local or remote `accepted`, the initial configuration is prepared in a task and integrated into `main` before the Human Owner authorizes the one-time creation of `accepted` from that verified commit. This creation is not a merge. Once `accepted` exists, changing its configuration requires a PR; never overwrite or move an existing `accepted`. Lowering the mode requires HAG-06.

| Setting | Value |
|---------|-------|
| Working mode | `Lite` <!-- Lite | Standard | Enterprise --> |
| Engine | `antigravity` <!-- antigravity | vscode | ai-studio --> |
| Project context | `work` <!-- work | personal --> |
| Git mode | `remote` <!-- remote | local --> |
| Working branch | `main` |
| Accepted branch | `accepted` |
| Review policy | `reviewer` <!-- reviewer | solo-owner (Lite only) --> |
| Stack | _to be defined in P0_ |

## 1. Sources of truth

The project state has exactly three sources:

1. **Project Memory** (`project-memory/`): intent, decisions and state. Authoritative.
2. **GitHub**: versioned code and history. `accepted` holds the accepted version.
3. **Graphify** (if enabled, `graphify-out/`): structural AST (0 tokens) and semantic relationships derived from the code, `inputs/`, and `dcp/` (excluding internal ASE paths via `.graphifyignore`). Never overrides the other two; queried locally in 0 tokens by `scripts/sync-inputs.py --query-graph` to detect God-Node coupling (`HAG-02`) and open-task impact (`T-NNNN`), while semantic `--update` runs on docs/images are gated by `HAG-04`.

External tools (Jira, Confluence, boards) are secondary: they may receive copies, never decide. If Project Memory and code diverge, report it; do not silently "fix" either side.

## 2. Project Memory, 3-Zone Workspace Layout (`.ase/` + Root `deliverables/` + `.vscode/settings.json`)

When installed into a repository via `install.py` (default), the workspace is organized into three zones and `.vscode/settings.json` (`files.exclude`) automatically hides internal ASE paths in the IDE Explorer sidebar:

```
repository-root/
├── inputs/                  ← Initial Context Inbox (checked FIRST by /ase-adopt, /ase-setup, /ase-plan; hidden on /ase-pack)
├── <project-files>          ← Zone 1: Project source code, tests, configs, README.md
├── deliverables/            ← Zone 2: Visible Stakeholder Deliverables (verified zero-ASE-footprint)
│   ├── INDEX.md                 ← Generated by /ase-pack in first-person singular ("I")
│   ├── 01-discovery/            ← P0-A as-is-report PDFs & discovery notes
│   ├── 02-planning/             ← P1–P4 project-plan PDFs & roadmaps
│   ├── 03-architecture/         ← P3 architecture-dossier PDFs & diagrams
│   ├── 04-verification/         ← P6–P7 reconciliation, test evidence & status reports
│   └── 05-release-and-handover/ ← P7–P8 release-report PDFs, PR descriptions & handover notes
└── .ase/ (plus .agents/ & .github/) ← Zone 3: Internal ASE Harness (hidden in IDE Explorer)
    ├── project-memory/
    │   ├── dcp/     ← design intent (NORMATIVE), sections 00–07 (waves/, features/, tasks/, user-stories/)
    │   ├── adr/     ← one file per decision, ADR-NNN-<slug>.md (NORMATIVE)
    │   └── state/   ← current state (DESCRIPTIVE, including state/reviews/ and state/PACK_STATE.json)
    ├── specs/       ← internal JSON input specs for build-stakeholder-pdf.py
    ├── scripts/     ← deterministic helpers (check-prereq.py, next-id.py, pack-workspace.py, export-handover.py, etc.)
    └── templates/   ← document and PDF templates
```

- **Normative** files (`dcp/`, `adr/`) change only through human approval (HAG-02 for architecture). Exception: the `status` and `correction_cycles` fields of task files in `dcp/04-implementation/tasks/` are descriptive, and non-HAG informational rows of `dcp/00-project-management/project-charter.md` (*Chi*, *Perché*, *Quando*, *Come* governance) and `dcp/03-design/conventions.md` may be updated row-by-row during Continuous Context & Memory Updates (`/ase-memo`, `/ase-context`, `/ase-plan`) without opening a `T-NNNN` task.
- **Descriptive** files (`state/`) are updated by agents at step 7 of the Iteration Protocol or during Continuous Context Updates (`state/CONTEXT_LOG.md`, `state/INPUTS_STATE.json`, `state/KNOWN_ISSUES.md`, `state/NEXT_TASK.md`) without approval.
- `state/TASK_LOG.md` and `state/CONTEXT_LOG.md` are append-only. `state/TRACEABILITY.md` is generated; never edit it by hand.
- Read only what the current task needs. Start from `state/NEXT_TASK.md` and the task file.

## 3. Git model

- `main` is the working branch. CI runs on every push when automation is configured; in a local-only project without CI automation, run the declared Fast CI command on `main` and record it as local gate evidence, not hosted CI.
- Agents in VS Code work on short branches `task/<ID>` and merge into `main` after the preliminary check with green CI.
- `accepted` must be protected where GitHub supports it: require a PR from `main`, the `gate / gate` check, and the configured review policy. **No agent ever merges into `accepted`** (HAG-01). With `Review policy` `reviewer`, the PR needs an approval from an eligible human other than its author; with `solo-owner` (Lite only, for single-person projects), no approving review is required, and the Human Owner's own merge after reading the PR is the HAG-01 approval.
- If repository plan or permissions make branch protection unavailable, the Human Owner may explicitly approve a procedural fallback under HAG-06, recorded in `project-memory/state/M0_CHECKLIST.md`. The procedure still requires a PR from `main`, a successful `gate / gate` run before the Human Owner merges, and a post-merge `bash scripts/verify-accepted.sh <PR-number>` audit. No agent merges into `accepted`. This fallback cannot technically prevent direct pushes or an early merge; record and accept that residual risk explicitly. If a distinct eligible reviewer is required by the configured `Review policy`, the fallback does not waive that requirement.
- One engine at a time writes to `main`.
- One Work Package is open on `main` at a time; its PR is opened when the WP is complete.
- Commit messages start with the task ID (`T-0117: ...`). PR titles start with the WP ID (`F-021: Upload PDF`).

### Local Git mode & Proactive Milestone Git Proposals (`scripts/git-advisor.py`)

With `Git mode` `local` (set by `/ase-adopt`), ASE runs on the Human Owner's machine inside an existing or local repository. The ASE files are encapsulated in `.ase/` and excluded from Git through `.git/info/exclude` unless `--versioned` was chosen.

- `Working branch` is the branch the Human Owner works on; `Accepted branch` is `none`. The team's own branch, PR, review and CI rules apply unchanged.
- **Proactive Milestone Git Advisor (`scripts/git-advisor.py`)**: At every milestone or task checkpoint (`m0`, `plan`, `task`, `review`, `release`), run `python3 scripts/git-advisor.py --milestone <m0|plan|task|review|release>` (or `.ase/scripts/git-advisor.py`) to inspect whether a GitHub remote is connected (`no-remote` vs `github-remote`), branch ahead/behind status, and `.ase-install.json` versioned state, and include its **Git Milestone Proposal** in the report.
- **Strict `work` vs `personal` Execution Policy**:
  - **`Project context: work`**: Agents **never execute** `git commit`, `git push`, `git rebase`, branch creation/switching, PR creation, or remote settings changes. They leave changes in the working tree and present the milestone-appropriate Git commands (with zero-ASE-footprint and first-person singular `"I"` commit/PR messages) for the Human Owner to run manually.
  - **`Project context: personal`**: Agents never commit or push *before* presenting the diff (`IN_REVIEW`). At the milestone/task report, agents present the `git-advisor.py` commands (`git commit`, `git push`, `gh repo create`, `gh pr create`, `git tag`, `gh release create` according to remote connectivity and milestone) and explicitly offer to execute them directly once the Human Owner confirms (`HAG-01`). Even in `personal` mode, **no agent ever merges into `accepted`**.
- `Fast CI command` and `Gate CI command` are the repository's existing commands (for example `npm test`, `mvn -q verify`), recorded by `/ase-adopt`. If a command is `none`, say so; never claim a check passed.
- A task becomes `DONE` when its criteria have evidence, the declared Fast command passes locally, and the Human Owner accepts the diff (HAG-01 in local mode). Until then it stays `IN_REVIEW`.
- Never put ASE IDs, Project Memory content or internal notes into code, commit messages or PRs in `work` or unversioned repositories unless the Human Owner asks.
- Sections about `main`, `accepted`, task branches and hosted workflows apply only to `remote` mode.

## 4. Work hierarchy and IDs

Project → Wave → Feature → User Story → Task. Every Work Package (usually a Feature) maps to exactly one PR.

| Type | Format | Type | Format |
|------|--------|------|--------|
| Requirement | `REQ-NNN` | User Story | `US-NNN` |
| Wave | `W-NN` | Task | `T-NNNN` (or WBS `T-NNNN.1`, `T-NNNN.1.1` for inserted inner sequences) |
| Feature | `F-NNN` | ADR | `ADR-NNN` |
| Other WP | `WP-NNN` | Defect | `BUG-NNN` |

IDs are flat, stable, sequential per type and never reused. When an interruption or discovery mid-roadmap requires inserting an inner sequence of prerequisite tasks inside or ahead of an existing task (e.g. `T-0008`), allocate WBS dotted sub-task IDs via `python3 scripts/next-id.py --type task --under T-0008` (`T-0008.1`, `T-0008.2`, `T-0008.1.1`) so later insertions are immediately recognizable. Hierarchy lives in the `parent` front matter field, external keys in `external`. Test names cite the `US-NNN` or `REQ-NNN` they verify.

For persistent application records, do not reuse identifiers while stale references could still target a replacement record. Prefer UUIDs or a database-supported non-reusing key (for SQLite integer keys, `INTEGER PRIMARY KEY AUTOINCREMENT`); test that a stale delete/update cannot affect a later record after deletion or clear-all.

## 5. Task execution

- Execute **one task at a time** with the Iteration Protocol (`dcp/04-implementation/iteration-protocol.md`): input, pre-implementation, planning, implementation, verification, reporting, state update, stop.
- Implement only the assigned task. No unrelated changes, no future tasks.
- **No change outside a task.** Every change to the repository (code, dependencies, configuration, documentation) happens inside a task file. If asked for a change with no assigned task, do not perform it: propose the task (goal, risk, criteria), create it with `/ase-plan` or the template, and wait until it is assigned. Each backlog-planning run of `/ase-setup` or `/ase-plan` opens its own task file (e.g. `T-0001: P0 setup`, `T-0012: plan W-02`), writes only within that task and logs it in `TASK_LOG.md` when closed. Creating a task file in `TODO` is how a task starts, so it is not a change outside a task. Read-only questions, analysis, and **Bucket 1 Continuous Context & Memory Updates** (`/ase-memo`, `/ase-context`, or `/ase-plan` Context Mode via `scripts/sync-inputs.py` updating `state/CONTEXT_LOG.md`, `state/INPUTS_STATE.json`, `state/KNOWN_ISSUES.md`, `state/NEXT_TASK.md` alerts/chains, and non-HAG informational rows of `project-charter.md` / `conventions.md`) need no `T-NNNN` task file; any Bucket 2 normative change (`HAG-02`..`HAG-06`) stops for human approval before modifying normative files or opening a `/ase-plan` task.
- Task states: `TODO → IN_PROGRESS → IN_REVIEW → DONE`, or `BLOCKED` / `PAUSED` (suspended on the Return Stack in `state/NEXT_TASK.md` while an inner WBS sequence `T-NNNN.1` runs) / `DEFERRED` (postponed to a later Wave) / `SUPERSEDED` (retired by a roadmap pivot).
- Each failed verification increments `correction_cycles`. **At the third failure the task becomes `BLOCKED`** and a human decides. In a local-only project without CI automation, a passing declared Fast CI command on `main` is the local gate evidence required for `DONE`; never describe it as hosted CI.
- On `DONE`, `BLOCKED`, `PAUSED`, `DEFERRED`, or `SUPERSEDED`, append one line to `state/TASK_LOG.md`.
- If the task conflicts with an ADR or the architecture, stop and report: do not decide alone.

## 6. Risk class

Every task has `risk: low | medium | high`.

| Class | Typical scope | Extra controls |
|-------|---------------|----------------|
| low | UI, copy, local refactoring covered by tests | Standard PR checks |
| medium | New business logic, new APIs, shared components | Integration tests, review by the relevant specialist |
| high | Auth, data model, migrations, dependencies, cost or latency | Relevant security/performance tests, Security Reviewer or Solution Architect, matching HAGs. For record deletion, include stale-reference tests where applicable. |

## 7. Human Approval Gates & Correlated Optimization Drivers

Decisions reserved to the human owner. Active gates depend on the working mode (`HAG-01` through `HAG-06` are all active in `Lite`).

| ID | Decision | Correlated Drivers | Lite | Standard | Enterprise |
|----|----------|--------------------|:----:|:--------:|:----------:|
| HAG-01 | Human merge of a `main → accepted` PR after Gate/review checks (`remote`), or human acceptance and commit of the task diff (`local`); procedural fallback requires HAG-06 | 🔺 Quality, 🔺 Traceability, 🔻 Blast Radius | ✓ | ✓ | ✓ |
| HAG-02 | ADRs, architectural changes, "as-is" baseline (M0-A), `/ase-plugin` scaffolds | 🔻 Debt & Coupling, 🔺 Reusability, 🔻 Cost | ✓ | ✓ | ✓ |
| HAG-03 | Auth, authorization, data model, destructive migrations | 🔺 Security & Privacy, 🔻 Attack Surface | ✓ | ✓ | ✓ |
| HAG-04 | Exceeding cost, latency, query/bytes-billed, or usage thresholds | 🔻 Cost (FinOps/Token), 🔻 Time (Latency) | ✓ | ✓ | ✓ |
| HAG-05 | New external dependencies or licenses | 🔻 Cost, 🔻 Coupling, 🔺 Security | ✓ | ✓ | ✓ |

## 8. Commands, Continuous Memory Aliases (`/ase-memo`, `/ase-context`), & Approval-Gated Reactive Command Chaining (`scripts/check-prereq.py`)

Every `/ase-*` command has a single non-overlapping responsibility and runs `python3 scripts/check-prereq.py --command <name>` at Step 0 and `python3 scripts/check-prereq.py --post --command <name>` at completion:
- **Upstream Prerequisite Chaining (Step 0 — Never a Dead-End Block):** If a prerequisite command is needed first (e.g., `/ase-export` called before `/ase-pack`, `/ase-task` called with no assigned task, or a cloned release folder detected for `/ase-switch`), record the `prerequisite_chain` in `state/NEXT_TASK.md` (`Pending Command Chain`), ask the Human Owner for approval to execute the prerequisite command first, and **automatically continue into the requested command** once approved.
- **Downstream Cascade Chaining (`--post`):** When a command finishes and triggers the condition for a downstream command (e.g., `/ase-memo` / `/ase-context` logs a `HAG-02`..`05` scope/architecture change requiring `/ase-plan`, `/ase-adopt` finishes M0-A and triggers `/ase-plan`, `/ase-plan` assigns a task and triggers `/ase-task`, `/ase-task` completes the last task of a Work Package and triggers `/ase-review`, `/ase-review` triggers `/ase-pack`, or `/ase-pack` offers `/ase-export`), combine the applicable HAG and chain prompt into a single question and execute the chained command upon approval.

| Command | Single Primary Purpose |
|---------|------------------------|
| `/ase-setup` | Lite P0 for a new GitHub project (`remote` Git mode, mutually exclusive with `/ase-adopt`): mode, engine, stack, branches, Project Memory, and the M0 checklist |
| `/ase-adopt` | P0-A Lite for an existing or local-only repository (`local` Git mode, mutually exclusive with `/ase-setup`): read the code, rebuild the minimal DCP, configure `.vscode/settings.json` (`files.exclude`), detect Umbrella child projects (`scripts/ase-topology.py`), and record the as-is baseline (M0-A, HAG-02) |
| `/ase-memo` *(alias: `/ase-context`)* | **Continuous Context & Memory Update (`scripts/sync-inputs.py`):** Incrementally ingest `inputs/`, call notes, and screenshots; auto-apply Bucket 1 non-HAG updates (`state/CONTEXT_LOG.md`, `KNOWN_ISSUES.md`, `NEXT_TASK.md` alerts, non-HAG `project-charter.md` rows) with zero task ceremony; query Graphify (`--query-graph`) in 0 tokens; dispatch `CONTEXT_MEMO_SYNC` handoffs in `orchestrator` mode; and gate Bucket 2 changes (`HAG-02`..`06`) before chaining to `/ase-plan` |
| `/ase-plan` | Propose an MVP and create or update an approved, traceable Lite backlog (including WBS inner sequences `T-NNNN.1` & Return Stack, `SUPERSEDED`/`DEFERRED` pivots, or `CONTRACT_AND_PLAN` `HANDOFF.json` dispatches in `orchestrator` mode); assign the next ready task in `NEXT_TASK.md` |
| `/ase-task` | Execute one assigned task with the Iteration Protocol, Fast CI, Return Stack advancement, and `HANDOFF.json` completion receipt (`member` mode) |
| `/ase-review` | Technical Work Package Quality Gate (`Gate CI`, traceability matrix, full diff review, DoD) and Git Pull Request (`main → accepted` PR in `remote` mode, or `state/reviews/<WP>-review.md` + `deliverables/05-release-and-handover/pr-description.md` in `local` mode) |
| `/ase-pack` | In-place post-work curation of `deliverables/` (`scripts/pack-workspace.py`): generate `deliverables/INDEX.md` in `"I"` voice, optional stakeholder PDFs from `.ase/specs/`, hide internal/empty folders via `.vscode/settings.json` (`files.exclude`), verify zero-ASE-footprint, and record `state/PACK_STATE.json` |
| `/ase-export` | Read-only external handover bundler (`scripts/export-handover.py`, requires a fresh `/ase-pack`): package clean `project-files/` + `deliverables/` into `handover/<project>-handover-YYYY-MM-DD/` and `.zip` |
| `/ase-switch` & `/ase-upgrade` | In-flight Change-Data-Capture (CDC) & row-by-row release switcher/upgrader (`scripts/switch-release.py` / `install.py --switch`): upgrade an ongoing project (and cascade across all `member` child projects in an Umbrella workspace) from an older ASE release to a newly cloned release in the workspace root while keeping unchanged files/rows untouched and deleting the old release & clone |
| `/ase-status` | Read-only daily project situation report (`scripts/project-status.py`): roadmap position, WBS inner sequence & Return Stack, Federated Umbrella rollup (`FEDERATION_STATE.json` / `HANDOFF.json`), daily delta, critical insights, Next Steps paragraph, `"I"` standup snippet, and optional report/PDF proposal |
| `/ase-plugin` | Scaffold, validate, and sync project-derived reusable domain plugins (`plugins/<slug>/`) with zero ASE dependency |

The full agent roster (DEC-05) is installed natively for both harnesses: `.github/agents/*.agent.md` for GitHub Copilot and `.agents/agents/*.md` for Antigravity. Start from `ASE Lead`; it delegates to specialists only when the task needs them. Skills live in `.agents/skills/` (read natively by both); file-scoped rules are in `.github/instructions/` (Copilot) and `.agents/rules/` (Antigravity). Agents follow this file; they do not add authority.

If the skill for a command is not installed, say so instead of improvising its behavior.

## 10. External-facing artifacts, stakeholder PDFs, and reusable domain plugins

1. **Zero ASE footprint on external-facing artifacts (`scripts/verify-external-clean.py`):**
   - Every artifact potentially shared with external people or systems (stakeholder PDFs `*.pdf`, exported domain plugins `plugins/**`, application code/schemas/queries, external documentation `docs/**`, and local-mode PR drafts `project-memory/state/reviews/*.md`) must be verified free of references to the ASE framework (`Agentic Software Engineering`, `ASE`, `agentic-dcp-template`, `dcp-template`, `Development Context Package`, `DCP`, `Project Memory`, `project-memory/`, `HAG-01`..`HAG-07`, `Human Approval Gate`, `Iteration Protocol`, `/ase-*`, `M0-A`, `.ase-install.json`, `ase-lead`).
   - Standard planning and requirement identifiers (`W-01`, `T-001`, `T-0001`, `REQ-001`, `F-001`, `US-001`, `WP-001`, `ADR-001`) are allowed in plans and stakeholder PDFs.
   - Run `python3 scripts/verify-external-clean.py <paths>` before marking a task `IN_REVIEW`/`DONE` or handing off an external deliverable, and record the `PASS` output.
2. **Optional stakeholder-level PDF documentation (`scripts/build-stakeholder-pdf.py`):**
   - At key milestones — P0-A adoption (`as-is-report`), P1–P4 planning (`project-plan`), P3 architecture (`architecture-dossier`), and P7/P8 review/release (`release-report`) — proactively offer to generate an optional stakeholder-level PDF using `templates/stakeholder-pdf-template.json` and `python3 scripts/build-stakeholder-pdf.py --spec <spec.json> --output <file.pdf>`.
   - Use `context_profile: "work"` (when `Project context` is `work`, applying the **Sopra Steria Group** brand color palette and corporate metadata) or `context_profile: "personal"` (when `Project context` is `personal`, selecting the palette preset best suited to the project domain).
3. **Proactive ASE-external reusable domain plugins (`/ase-plugin` & `scripts/sync-plugin.py`):**
   - When the project uses domain-specific guardrails, multi-tool stack conventions, or deterministic validators that could be reused across similar projects, proactively propose packaging them into `plugins/<plugin-slug>/` (HAG-02) via `/ase-plugin`, completely decoupled from ASE.

## 11. Communication voice, authorship ("I", never "We"), & Single-Channel Output Rule

1. **ASE has no voice or co-authorship:** ASE is an internal engineering harness, never a speaker or team member.
2. **In direct conversation with the Human Owner:** Address the Human Owner as `"you"` (`"tu"`) and refer to your own agent actions in first-person singular (`"I"` / `"Io"`). **Never** use collaborative first-person plural (`"we"`, `"us"`, `"our"`, `"noi"`, `"abbiamo"`) to describe work done in the project.
3. **In all drafted messages, answers, emails, commit messages, PR descriptions, review summaries, and stakeholder documents proposed for the Human Owner:** Write strictly in the **Human Owner's first-person singular voice (`"I"` / `"Io"` / `"Ho..."`)** — never `"we"` / `"noi"` / `"abbiamo"`. Verify drafted handover/review files with `python3 scripts/verify-external-clean.py --check-first-person <paths>` (automatically enforced on `05-release-and-handover/` and `state/reviews/`).
4. **Single-Channel Output Rule (Write in Document OR Write in Chat — Never Both; Zero File Mirroring):**
   - Autonomously choose **one** output channel per response:
     - **Ephemeral / Conversational Content:** Short answers, status checks, clarifications, and HAG approval prompts are written **only in chat** (create zero files).
     - **Persistent Documents:** Plans, DCP sections, ADRs, review reports, and questionnaires are written **only once to their single canonical file on disk**, and in chat output **at most a 2–4 line pointer** with the clickable file link (`[basename.md](file:///...)`) telling the Human Owner to read the document there—**never** repeat, copy, or re-summarize the document body in chat unless explicitly asked.
   - **Zero Duplicate File Mirroring:** Never write or mirror the same document into multiple folders (e.g., never create duplicate files in both `docs/` and `deliverables/02-planning/`).
5. **Federated Multi-Project Hierarchy (`scripts/ase-topology.py` & `HANDOFF.json`):**
   - In an Umbrella Parent Directory containing sub-projects (`role: orchestrator`), the Father `ASE Lead` acts **strictly as a conversational orchestrator**: it never reads or edits child source code or child tasks directly, reads only `state/FEDERATION_STATE.json` (`ase-topology.py --rollup` in `0` LLM tokens), proactively asks approval to onboard `unmanaged_child` folders (`--onboard-child`), and dispatches orders exclusively via `<child>/.ase/project-memory/state/HANDOFF.json` (`--dispatch`).
   - Child projects (`role: member`) remain 100% operable standalone while reading/completing `HANDOFF.json` entries (`--ack`, `--escalate`, `--complete`).

## 12. Optimization Drivers & Command-Level Priorities

Every plan, implementation, and review must actively optimize **5 Factors to Reduce** and **5 Factors to Augment**, prioritized by lifecycle command and task risk class:

- **5 Factors to Reduce (Minimize):**
  1. **Cost (`HAG-04`, `HAG-05`):** Token usage (minimal targeted context), cloud/query FinOps cost (avoid N+1 queries, full-table scans, redundant API/LLM calls), and external dependencies (prefer standard library / existing stack).
  2. **Time (`HAG-04`, `HAG-06`):** Cycle time (small vertical slices), runtime latency, and `Fast CI` execution time.
  3. **Human Cognitive Load & Friction (`HAG-01`):** Clean 3-Zone workspace (`.vscode/settings.json`), decision-first reports, ready-to-run `git-advisor.py` commands, and one-step `/ase-pack` / `/ase-export`.
  4. **Blast Radius, Attack Surface & Rework (`HAG-01`, `HAG-03`):** Single-task diffs, least privilege, `PAUSED` Return Stack (`T-NNNN.1`), and max 3 `correction_cycles`.
  5. **Technical Debt, Coupling & Boilerplate (`HAG-02`, `HAG-05`):** Reuse existing modules before creating new abstractions; retire obsolete scope via `SUPERSEDED`/`DEFERRED`.
- **5 Factors to Augment (Maximize):**
  1. **Quality, Correctness & Determinism (`HAG-01`):** Verifiable tests (`REQ-NNN`/`US-NNN`), edge-case coverage, idempotency, and non-reused persistent IDs.
  2. **Security, Privacy & Trust Boundaries (`HAG-03`):** AuthN/AuthZ, input validation, parameterized queries, secrets isolation, and `verify-external-clean.py`.
  3. **User Usability & Ergonomics (`UX / DX`):** Clear UI/dashboard states (loading, empty, error, success), accessibility, actionable CLI/API errors, and intuitive defaults (enforced directly by active Lite roles without extra subagent overhead).
  4. **Reusability & Portability (`HAG-02`):** Clean module boundaries and zero-ASE-dependency `/ase-plugin` extraction.
  5. **Traceability & Stakeholder Clarity (`HAG-01`, `HAG-07`):** `TRACEABILITY.md`, `/ase-status`, `"I"` voice consistency, and executive `deliverables/`.

| Command / Context | Primary (Dominant) Drivers | Secondary (Guardrail) Drivers |
|-------------------|----------------------------|-------------------------------|
| `/ase-setup`, `/ase-adopt` | 🔻 Friction, 🔺 Security/Trust Boundaries, 🔻 Time-to-Start | 🔺 Reusability, 🔺 Stakeholder Clarity |
